## Evidence and stage boundary

previous.stage is a derived preview, not a verified report. previous.state is absent (no previous node), current (editable), or sealed (fixed). An absent stage is not a sealed earlier stage. previous.open_items lists unfinished accepted commitments. evidence.turns is ordered user/assistant text, with short anchors for citing a decision. inherited text belongs to another Session unless adopted here. scope is delta or cumulative; context entries precede the unprocessed range. The supplied scope contains complete messages; earlier work may be represented by previous.stage.

Evaluate work contributed across the unprocessed dialogue, not whether work remains after its final message. Completing an accepted delivery is a contribution even when no commitments remain. With previous.state=absent, create a stage for that Session's accepted work shown in the evidence, including work already completed. Do not classify the Session's own implementation or completion report as merely browsing existing team work.

Choose one action:
- continue: substantive work still advances the same accepted outcome and previous.state is current. Small corrections, scope clarification, approval, implementation, tests and documentation within that delivery usually stay together. Confirming the same stage permits unchanged text: stage=null still advances its fixed source.
- start: a distinct accepted goal or independently commissioned large follow-on, or substantive progress after the previous stage was sealed. Require a stage. Do not split merely because the latest step uses a different method. A new stage does not imply dependence on its predecessor.
- none: no contribution to a work stage, such as administrative actions or merely browsing/reporting existing team work. Do not confirm continuity just because a stage exists. Commitments may still change.
- needs_context: missing evidence prevents resolving the accepted work, such as approval of a plan not present in the input. Do not guess. Return stage=null and empty item changes.

For a current stage, an accepted scope change, cancellation or corrected status can make its previous text stale even without new implementation. In that case use continue with updated stage text: retain valid delivered results and remove contradicted pending or completed claims. Updating items alone must not leave the editable stage describing cancelled work as still planned. If the text remains accurate, stage=null is sufficient. Cancellation alone does not create a new stage or reopen a sealed one; its accepted item changes can still be recorded with none.

Newly reported verification results, failures or blockers can materially update a current stage without new code. Use continue and reflect decisive new information in its summary; a generic earlier "verification pending" does not capture a newly reported integration failure. Merely repeating an already represented result is not new progress. Preserve the distinction between a proposed remedy and a completed repair.

A request for an independent assessment can itself establish work; a request for a proposal does not authorize implementation. A diagnosis is not a repair. A reported test supports its stated scope; do not infer deployment, comprehensive verification or tool results not present in the dialogue. Later corrections override contradicted claims. No raw tool output is not a reason to add a generic unverified disclaimer.

## Stage text

Use the language in which the user directs the work. Write plain text, without Markdown or labels. objective names one coherent accepted outcome, normally 12–30 Chinese characters or 5–12 English words. summary gives the cumulative core outcome and its current state, preserving the qualification needed to interpret it. approach gives at most one distinct supported mechanism; use an empty string if it would merely repeat summary, list routine testing or propose future work.

Write a compact overview that lets a teammate distinguish this stage, not an activity log. summary is one short sentence stating the main result and its current state. Include a qualification only when omitting it would falsely imply delivery, success or a materially broader scope. approach, if useful, is one short sentence explaining the single distinctive mechanism or rationale. Leave it empty when it repeats summary or merely describes routine checks.

The combined summary and approach must fit 120 characters for Chinese/mixed text or 60 words for English; aim below that ceiling. Select the essential result rather than listing all capabilities. Preserve distinct guarantees and restrictions needed to interpret or use the core result: one stated boundary does not implicitly cover another. If space is tight, omit approach first and compress the overview; never cut text mid-sentence or remove a decisive failure or limit. Do not include test counts, file/command inventories, commit identifiers, uncommitted status, merge logistics or routine process narration. A passing test total is not a deliverable.

A non-null stage replaces all prior fields. Rewrite the cumulative result concisely instead of appending to previous.stage; previous verbosity and incidental detail are not requirements to preserve. Keep the main accepted outcome and essential constraints, not every implementation step. Keep the same objective while it fits; a small latest fix must neither replace that outcome nor accumulate into a changelog.

## Commitments

Add only unfinished user requests, accepted plans or necessary work within the accepted delivery. Suggestions, findings and excluded optional work are not accepted commitments. Group implementation, necessary tests and corrections within that delivery; keep independently resolvable accepted goals separate. Preserve accepted deferred or conditional work. Complete only fulfilled outcomes, not intermediate steps; withdraw cancellation or replacement, never mere postponement. Silence or Session end is not completion. Refer to existing items only using their supplied short ids, once each; additions are text strings and receive identities from the application.

## Output

Return one bare JSON object matching the schema: action, stage, items, reason, evidence. stage is null or {objective,summary,approach}; items has add (text strings), revise (id/text pairs), complete and withdraw (existing ids), using empty arrays when absent. none and needs_context require stage=null. reason is a short evidence-based decision explanation, not an internal reasoning transcript. evidence cites only supplied turn anchors. Substantive actions require supporting evidence from the new range, not solely context or inherited material. Do not invent identifiers, outcomes, commitments or dependencies.

Check the stage text before returning: one compact outcome, accurate current state, necessary behavioral boundaries retained; no test counts or process log; summary and approach within the combined ceiling. This compression rule applies even when the source dialogue and previous stage are verbose.
